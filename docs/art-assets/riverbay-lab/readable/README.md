基于 `00eddef5ef500384f1997cb296c8383b917a31a6`，保持同一人工布景、镜头、原草纹理、26% 低频叠加、水 v2、稀疏杂物。A 仍是原等宽结构版；B 只多开 `shoreVariation`。默认全部关闭，不接入正式 `index.html`，不改 `js/`、`assets/`、玩法或碰撞，没有付费生图或新贴图。

## 本次修正

- 湿沙宽度由 4–14 改为 8–14，浅水由 6–18 改为 8–18 个世界屏幕像素。0.75 倍镜头的基础湿沙下限约 6 显示像素；这只是几何下限，实际可读性仍受缩放采样、遮挡与颜色影响。
- 陆/水核心层 alpha 为 `.48/.45`，外层仍 `.14/.12`；内层 `.30/.24` 改用更深的颜色。alpha 是单层参数，不是多层重叠后最终像素不透明度。
- 颜色周期为 `x+y` 的 14 单位，渐变轴从 `T2S(0,0)` 到 `T2S(N,N)`，与世界坐标色域对齐。每周期至少 8 个区间，32 格场景为 38 色标。原先固定五色标，恰好每点差 14 个 `x+y` 单位，直接换周期会采成同色；新增回归覆盖这一混叠问题。宽度 reach 仍是 22/26 格的平滑正弦组合。
- 每条岸线只生成一次六组同向三角命令；浏览器支持 Path2D 时，把需要的路段联合写入一次组合路径后缓存。组合缓存最多 24 项，拓扑失效或换世界时全部重建；不新增地面画布。没有移除小池塘防相消或出口端帽。
- 独立审查发现 native `Path2D.addPath` 的组合在棋盘式水陆点接触处会改像素，因此没有使用它。改成一次直接写入原三角命令，仍是单次 nonzero fill 联合填充；检查棋盘和四出口、3 种缓存比例、全刷/局部编辑/重建，共 18 个对照逐字节一致。

## 串行性能

下表是现有 VM 的最终串行一轮 native 中位数（ms），各版本/阶段 12 个 B 样本，完整样本、P95 和分段见 [benchmark.json](benchmark.json)：

| 阶段 / 指标 | 旧 B | 新 B 命令回放 | 新 B Path2D |
|---|---:|---:|---:|
| 重建拓扑：同步总帧 | 136.620 | 139.485 | 139.951 |
| 重建拓扑：构建提交 | 36.978 | 39.601 | 38.443 |
| 已缓存几何切换：同步总帧 | 136.231 | 135.775 | 131.966 |
| 已缓存几何切换：构建提交 | 36.422 | 35.676 | 31.207 |

在本次 native 记录里，Path2D 复用减少了重复构建提交：对同图命令回放约少 4.5ms，总调用约少 3.8ms。**首次拓扑构建未改善**，新 B 约 140ms，旧 B 约 137ms；不能声称首帧问题已解决。新 B 已缓存切换仍比同轮 A 中位数 118.485ms 多约 13.5ms，尚未达到接近 A 的目标。

新 B Path2D 的 40 暖帧 P95 为 1.976ms，0 次地面重建。已缓存切换的三角/组合路径新增构建数均为 0；历史版本没有这些计数器，用 null 明确标记，不能把“未测”写为零。

这是一台共享 VM 的单轮 native 结果；不要与旧 B 浏览器的 42–65ms 或暖 P95 0.6ms 直接换算，也不能据 drawImage 同步时间判定 GPU 原因。三段各自中位数不一定相加等于总帧中位数。

## 浏览器复测（已补，2026-10-18）

作者环境当时起不了静态服务，改用可由第三方复现的本地 Chromium 补测，记录与 7 张图在 [browser-readable](../browser-readable/browser-acceptance-readable.md)。同机位 0.75/1/2 与 390×620 DPR2 的 A/B 都做了，第四开关单独切换、拖走再拖回、控制台错误也检查过。

- **窄岸修复成立**：0.75 倍村庄前沿、2 倍田边与岛屿沿岸都能看到连续沙带；岛屿南岸剖面上，湿沙相对草地的 ΔR 从旧 B 的 `+2` 回到 `+21`（A 是 `+34`），约恢复六成。
- **仍偏淡**：湿沙整体还比 A 淡约三分之一；浅水层在东岸只有 `104/134/117` 就直接进水色，A 还有一段浅青过渡。
- **颜色**：2 倍下能看出灰绿到暖沙的轻微偏移，幅度克制。
- **首帧**：冷启动 40.1–60.4ms 与旧 B 的 43.7–57.9ms 差异落在噪声内（首次构建仍未改善）；已缓存切换 35.2–48.3ms 比旧 B 的 42.5–55.3ms 快约 7–10ms；相对 A 仍多 3–16ms。测量时机器 load average ≈ 58，绝对值偏高，只做同会话配对比较。
- **暖帧** p50 `0.3ms`、p95 `0.8ms`；**27 秒拖动本轮不采信**——A 和 B 都有 0.4–4.0 秒停顿，属机器负载，需安静环境重测。
- 拖走再拖回逐像素一致；`shore=false` 时切第五开关 0 次重建；窄屏无横向溢出。

恢复后针对 `7847d65` 重新通过 34 组地表（含 native 像素）、12 组控制器、8 组计时器、ground-cache-budget、8 组 terrain-presentation、10 组 mountain-render 和全部改动 JS 的语法检查；像素日志与本目录 `pixel-tests.txt` 逐字节一致。独立代码复审未发现阻断，并额外验证组合路径超过 24 项后的淘汰/重建能够完整复原路径命令。性能文件的候选源码 SHA-256 与当前 `terrain.js` 一致，未把已有记录伪称为新一轮计时。

同机位 0.75/1/2、390×620 DPR2 的 A/B 已由上面这轮补上（窄处湿沙可见、宽窄变化仍在、拖回稳定）。仍未完成：安静机器上的 12–30 秒拖动分位（本轮被机器负载污染）、实体手机触摸/热量/真实帧率、美术签字。

## 复现

```sh
node tests/riverbay-lab.js
node --expose-gc tests/riverbay-lab.js --pixels
node tests/riverbay-lab-app.js
node tests/riverbay-lab-profile.js
node tools/riverbay-lab/render.cjs --out /tmp/readable-native
node tools/riverbay-lab/benchmark.cjs --baseline-root /path/to/00eddef-checkout --compare-fallback --out /tmp/readable-benchmark.json
```

benchmark 串行交错旧 B、新 B 命令回放、新 B Path2D，分别记录拓扑重新构建与缓存几何的 A/B 切换；每类 12 对，先丢弃 3 对预热，再各取 40 暖帧。资产/JIT 并非进程冷启动，没有在计时段做截图或像素读回。它只能测 native 同步调用耗时，不测浏览器 GPU、异步呈现或 FPS。
